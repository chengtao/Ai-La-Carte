AI La Carte iOS App — Design Doc (v1)
0. Goals and Non-Goals
Goals

Deliver a “magic moment” recommendation with minimal friction:

GPS shortcut when restaurant menus exist

Camera scan fallback for any menu

Build a compounding experience:

Remember user preferences (taste profile)

Learn from implicit signals + light explicit feedback

Reduce server burden by helping guests decide quickly (augmentation, not replacement).

Non-Goals (v1)

Real-time POS integration

Full social feed / reviews platform

Full menu editing tools for restaurants

Payments / reservations inside the app (can link out later)

1. Product Overview
1.1 Primary User Story

User opens app → Welcome explains value and permission requests

Main view shows camera + nearby restaurants (if menus on file)

User either:

selects nearby restaurant → skip photo → quick session preference → compute → recommendations

takes menu photos → review + submit → session preference → compute → recommendations

After dining, user receives push → quick feedback (👍 / 👎 / didn’t order) to improve taste profile.

1.2 Key UX Principles

Camera-first; account is optional until after value is shown

Location used as suggestion, not assumption

Keep session preference ultra-light (two sliders)

Make “computing” screen delightful and trust-building

Reasons for each recommendation are mandatory (“why this for you”)

2. UI Structure and View Flow
2.1 Views (SwiftUI recommended)
A) WelcomeView

Purpose: Explain value, request permissions with rationale.

Content

Value proposition (bullet + simple graphic)

“We ask for Location to suggest nearby menus”

“We ask for Camera to read menus”

Buttons:

Continue (triggers permissions sequence)

Maybe later (lets user proceed with limited mode: manual search + camera later)

Permission flow

Request location (WhenInUse)

Request camera

Optional: push notifications request deferred until after first recommendation or after first “save profile” prompt

B) MainView (Camera + Nearby Restaurants)

Layout

Full-screen live camera preview

Top-right: Account icon

Top overlay: “Are you at X?” + scrollable list

Bottom center: large capture button

Behavior

On open:

Start camera session immediately (if camera permission granted)

Fetch nearby restaurants with menus (if location permission granted)

Nearby overlay:

Shows “Most likely” restaurant at top if confidence high

Scroll list of nearby restaurants with menu coverage badges:

Food menu ✅

Wine menu ✅

Updated: “2d ago”

Tap restaurant → creates session with restaurant_id and jumps to SessionPreferenceView

Capture:

Takes one photo at a time → goes to PhotoReviewSheet

Options: Retake / Next Photo / Recommend / Cancel

Each accepted photo is uploaded immediately with session ID

Recommend triggers SessionPreferenceView (if photos exist)

Edge states

No location permission → overlay shows “Enable location for nearby menus” + button

No camera permission → show static UI with button to enable camera; still allow restaurant selection flow

C) PhotoReviewSheet (per photo)

Actions

Retake

Accept

Cancel session

If accepted:

Upload photo to backend: POST /sessions/{id}/photos

Add to session local state

Buttons:

Next Photo (go back to camera)

Recommend (go to SessionPreferenceView)

D) SessionPreferenceView

Two sliders (1–5), minimal friction:

Adventurous ↔ Classic

Non-spicy ↔ The spicier the better

Actions

Continue → triggers recommendation job:

POST /sessions/{id}/preferences

POST /sessions/{id}/recommendations:generate

E) CalculatingView (Animated Status)

Displays sequential steps (front-end staged)

Uploading photos for processing…

Collecting public reviews from other websites…

Calculating your taste based on:

slider input

visit history

what you tapped / expanded

Making recommendation based on:

menu + reviews + your taste

Implementation detail

The view polls job status:

GET /sessions/{id}/recommendations/status

UI shows progress steps based on status enum, with smooth animations.

F) RecommendationView

Sections

Food recommendations (3–5)

Each item:

name

short explanation

“Why” badges (community favorite, chef signature, matches your spice tolerance, etc.)

optional wine pairing links (if wine menu present)

Wine recommendations (3–5)

safe / fun / splurge categories (optional)

each includes reason and “pairs with X dish”

Interactions (tracked)

Tap dish → detail view (optional v1)

Expand explanation (tracked)

Save/bookmark (optional v1)

Indicate “I ordered this” (optional quick CTA; can be deferred to push survey)

G) SurveyView (Post-dining feedback)

Triggered by push notification ~2 hours after session created (or configurable).

For each recommended item (top 1–2 items):

👍 Loved

👎 Not for me

🚫 Didn’t order

Optionally:

“Too spicy / Too heavy / Too sweet” chips (v1.1)

7. API Layer (REST Contracts)

All responses JSON. Use Bearer auth when signed in; allow anonymous device sessions.

7.1 Auth
POST /auth/apple

Request: { token: String, device_id: String }
Response: { access_token, user_id }

POST /auth/logout

Response: { ok: true }

DELETE /users/me

Response: { ok: true }

8. Recommendation & Modeling Design
8.1 Inputs

Parsed menu items (from photos OR existing restaurant menu DB)

Public review signals (cached summaries; not raw scraping in real-time if avoidable)

User profile (taste vector)

Session preferences (2 sliders)

Community popularity stats (views, saves, positive feedback counts)

8.2 Taste Profile Model (Practical v1)

Represent as a vector of normalized dimensions (0–1):

adventurousness

spice_preference

richness_preference (optional future)

sweetness_preference (optional future)

acidity_preference (wine)

oak_preference (wine)

Update rules:

Session slider inputs push adventurous/spice directly (strong weight)

Implicit signals (taps/expands) apply weak positive evidence

Feedback (loved/disliked) applies strong gradient update

Not ordered is neutral/weak negative (don’t over-penalize)

8.3 Ranking Approach (v1 Hybrid)

Retrieval: shortlist menu items by:

popularity

review sentiment

“signature” heuristics

Scoring function:

match(user_profile, item_attributes)

incorporate session slider overrides

incorporate community popularity

LLM role:

generate explanations

infer item attributes (spicy/rich/adventurous) from description/reviews

propose pairings between chosen food and wines

8.4 “Reason” Generation Rules

Every recommendation must include 2–3 reasons from:

Community favorite

Chef’s signature / house specialty

Best match for your spice/adventurous setting

Similar to dishes you engaged with before

Great value / crowd-pleaser

Wine pairing harmony (acid cuts fat, etc.)

Reason tags should be deterministic + auditable, not pure hallucination:

tie to real signals (popularity count, review summary, menu keywords)

9. Menu Processing Pipeline (Photos)
9.1 OCR + Parsing

OCR extracts text blocks

Parser segments into sections:

Appetizers, Mains, Desserts

Wine: Sparkling, White, Red, etc.

Normalize items:

name

price

brief description

Store as menu version with timestamp and confidence

9.2 Session Photo Joining

Photos uploaded with session_id

Backend asynchronously parses and attaches parsed menu to session context

If restaurant selected and menus exist, photo parsing can be skipped or used to detect specials.

10. Push Notification + Survey Loop
10.1 Trigger Strategy

When recommendations generated:

backend schedules push ~2 hours later (or configurable)

If user not opted into push:

schedule local reminder (optional) or show “feedback banner” next app open

10.2 Survey Content

Focus on top 1–2 recommended items (reduce load)

3-button outcome (Loved / Disliked / Didn’t order)

This feeds taste profile updates and improves future ranking.

11. Privacy, Permissions, and Trust
11.1 Location

used only for nearby restaurant suggestion + confidence scoring

no continuous tracking; request “When In Use”

11.2 Camera

used to read menus; images uploaded for processing

clarify retention:

store only for processing or keep anonymized to improve menu database (configurable)

allow user to delete session history

11.3 Reviews

Prefer cached summaries / licensed data sources rather than live scraping

Ensure the UI copy says “public review signals” not naming specific sources unless licensed.

13. Implementation Notes for the Coding Agent
13.1 iOS Tech Stack

SwiftUI + Combine (or async/await)

MVVM + Coordinator for navigation

AVFoundation for camera

CoreLocation

Push: APNs + device token registration

Persistence: SwiftData preferred

13.2 Key Engineering Risks & Mitigations

Camera performance: keep preview smooth, offload compression/upload in background task

Upload reliability: resumable uploads if possible; at minimum retry with backoff

Recommendation latency: use job + polling; show staged “calculating” steps

Wrong restaurant selection: always allow “Not here / scan instead” escape hatch
